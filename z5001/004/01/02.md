For a **1-day (8-hour) fast-track training**, I recommend a **hybrid approach**. Writing every line from scratch is usually not the best use of time, but simply running pre-written code is also not engaging.

A good balance is:

| Activity        | Time      | Approach                              |
| --------------- | --------- | ------------------------------------- |
| Explain concept | 10–15 min | Slides/whiteboard                     |
| Live coding     | 15–20 min | Write the core logic yourself         |
| Demo            | 10–15 min | Use prepared code with extra features |
| Lab             | 20–30 min | Students modify or complete the code  |

### Why not write everything live?

For modules like `argparse`, `socket`, `threading`, and `asyncio`, typing every line consumes a lot of time:

* You spend time fixing typos.
* Students wait while you type.
* One small syntax error can derail the flow.
* You may not finish all planned topics.

### Why not use only prepared code?

If you only open a completed project and explain it:

* Students don't see the thought process.
* It feels like reading someone else's code.
* They often struggle to recreate it later.

### A practical teaching pattern

For each topic:

1. Start with a skeleton project.
2. Write the important parts live.
3. Switch to the completed version for advanced features.
4. Let students extend it in a lab.

For example, with `argparse`:

* Open a file containing only imports and a `main()` function.
* Live code:

  * Create `ArgumentParser`
  * Add one argument
  * Parse arguments
  * Print the result
* Then switch to the completed version showing:

  * `--help`
  * `choices`
  * subcommands
  * validation
* Give students an exercise to add a new command.

Similarly, for sockets:

* Live code a simple echo server.
* Show one client connecting.
* Then open the prepared threaded version and explain only the new threading-related code.
* Finally, let students add a small feature, such as a timestamp or client ID.

### My recommendation for an 8-hour corporate session

Aim for roughly:

* **30% live coding** (core ideas and APIs)
* **50% prepared demonstrations** (complete, polished examples)
* **20% student exercises** (small, focused modifications)

This keeps the pace high while still showing how the code is built.

You're thinking about the right problem. In a **1-day corporate training**, your biggest constraint is **time**, not content.

If you allocate 20–30 minutes for every lab, you'll almost certainly fall behind. Some participants will finish in 5 minutes, while others may take 45 minutes or more. Then you'll have to choose between helping individuals and covering the remaining modules.

For this kind of session, I would avoid long independent labs. Instead, use **guided micro-exercises**.

For example:

* Explain the concept (10 minutes).
* Live code the essential part (10–15 minutes).
* Ask participants to make **one small change** (2–5 minutes).
* Review the solution together (2–3 minutes).
* Move on.

The changes should be very small, such as:

* Add a new command-line option to an `argparse` program.
* Change a shell command executed by `subprocess`.
* Modify the server to send a different response.
* Start two client connections instead of one.
* Change `asyncio.sleep(1)` to `asyncio.sleep(3)` and observe the behavior.

These exercises are short enough that almost everyone can complete them, and if someone doesn't, you can immediately show the solution without delaying the schedule.

## Keep "checkpoint" versions ready

Have folders like:

```text
01-cli
    step1
    step2
    final

02-subprocess
    step1
    step2
    final

03-socket
    step1
    step2
    final
```

If anything goes wrong—typing mistakes, environment issues, or time overruns—you simply open the next checkpoint and continue. This prevents the entire session from stalling.

## A realistic time budget

For an 8-hour day (about 7 hours of teaching after breaks), plan something like:

* 10–15 min: Concept
* 10–15 min: Live coding
* 5 min: Guided modification
* 5–10 min: Q&A and recap

That's roughly **30–40 minutes per topic**, which is much easier to manage than full labs.

### My recommendation

Treat this as a **demonstration workshop**, not a classroom lab. Your primary goal is that participants:

* understand the concepts,
* see working code,
* know how the pieces fit together,
* and leave with the complete source code to practice later.

For a one-day fast-track course, that is usually a more realistic and valuable outcome than expecting everyone to complete substantial exercises during the session.
