What you're seeing is expected from the current design.

After both clients disconnect, the **admin thread is blocked here**:

```python
address, client, msg = message_queue.get()
```

`queue.get()` waits forever for the next client message. Since there are no clients left, typing:

```text
SHUTDOWN
```

does nothing because **the program is not waiting on `input()` anymore**—it's waiting on the queue.

## Better Design

Separate the responsibilities into **two independent threads**:

```
Server
│
├── Accept Thread
│
├── Client Handler Threads
│      recv()
│      queue.put(...)
│
├── Message Dispatcher Thread
│      queue.get()
│      send message to admin
│
└── Admin Thread
       input()   <-- always waiting for commands/replies
```

The admin thread should **always** be reading the keyboard. It should not wait for client messages.

A simple approach is:

* **Message Queue**: client → admin
* **Reply Queue**: admin → client

Then:

* Dispatcher prints pending messages.
* Admin can type:

  * `reply <client-id> <text>`
  * `end <client-id>`
  * `shutdown`
  * `clients`

This is much closer to how real servers work.

### Even Simpler for Classroom

Don't mix **replies** and **admin commands** in the same prompt.

Instead, use commands like:

```text
Admin> clients
```

```text
Admin> reply 1 Hello
```

```text
Admin> end 1
```

```text
Admin> shutdown
```

Meanwhile, incoming messages are simply printed asynchronously:

```text
[1] father
[2] appa
[1] son
[2] mama
```

Now the admin console is **always active**, so `shutdown` works whether there are zero clients or one hundred clients.

---

I recommend rewriting the server this way because it's **cleaner**, avoids blocking on `queue.get()`, and demonstrates a proper command-driven server that resembles real administration consoles.
