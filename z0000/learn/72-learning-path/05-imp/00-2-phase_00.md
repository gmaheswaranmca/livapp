# Response 1 — Phase 0 (Domain Modeling / Bounded Context Design)

Before writing code, we design the business.

This is **Domain-Driven Design (DDD)**.

The purpose:

* Define boundaries
* Decide ownership
* Prevent tightly coupled services
* Identify events before APIs
* Prepare for Saga later

---

# Step 1 — Identify Bounded Contexts

We split the domain into independent business capabilities.

## 1. Order Context

Responsible only for orders.

Owns:

* Create order
* Validate order
* Track order state
* Start saga
* Maintain order lifecycle

Possible statuses:

```text
Created
Pending
InventoryReserved
PaymentAuthorized
ShippingCreated
Completed
Cancelled
```

Main rule:

Order service does NOT manage stock, payment, or shipment data.

It only owns order decisions.

---

## 2. Inventory Context

Responsible only for stock.

Owns:

* Available stock
* Reserve stock
* Release stock
* Stock deductions

Statuses:

```text
Available
Reserved
Released
OutOfStock
```

Inventory should not know how payment works.

---

## 3. Payment Context

Responsible only for money.

Owns:

* Payment authorization
* Capture payment
* Refund payment

Statuses:

```text
Pending
Authorized
Captured
Failed
Refunded
```

Payment service should not manage shipping.

---

## 4. Shipping Context

Responsible only for delivery.

Owns:

* Shipment creation
* Label generation
* Dispatch
* Delivery tracking

Statuses:

```text
Pending
Created
Packed
Dispatched
Delivered
Cancelled
```

---

# Step 2 — Context Map

Interaction relationships:

```text
Order
 ├── publishes OrderCreated

Inventory
 ├── consumes OrderCreated
 ├── publishes InventoryReserved

Payment
 ├── consumes InventoryReserved
 ├── publishes PaymentAuthorized

Shipping
 ├── consumes PaymentAuthorized
 ├── publishes ShipmentCreated

Order
 ├── consumes ShipmentCreated
 ├── marks order completed
```

This is the context map.

---

# Step 3 — Aggregates

Each bounded context has aggregate roots.

## Order Aggregate

```text
Order
 ├── OrderId
 ├── CustomerId
 ├── Items
 ├── Amount
 └── Status
```

Aggregate root:

Order

Child entities:

* OrderItem

Rules:

* Cannot pay cancelled order
* Cannot ship unpaid order

---

## Inventory Aggregate

```text
Inventory
 ├── SKU
 ├── QuantityAvailable
 └── QuantityReserved
```

Rules:

```text
available >= requested
```

---

## Payment Aggregate

```text
Payment
 ├── PaymentId
 ├── OrderId
 ├── Amount
 └── Status
```

Rules:

* Cannot refund uncaptured payment

---

## Shipment Aggregate

```text
Shipment
 ├── ShipmentId
 ├── OrderId
 └── Status
```

# Step 5 — Event Flow (Happy Path)

```text
Customer places order

OrderCreated
   ↓

InventoryReserved
   ↓

PaymentAuthorized
   ↓

ShipmentCreated
   ↓

```

That is your future saga path.

# Step 6 — Failure Flow (Compensation Thinking)

Suppose payment fails.

```text
OrderCreated
   ↓

InventoryReserved
   ↓

PaymentFailed
   ↓

InventoryReleased
   ↓

OrderCancelled
```

Compensation begins here.

This prepares Phase 3.

---

# Step 7 — Ownership Rule (Critical)

Golden rule:

"Only owner writes."

| Data      | Owner Service     |
| --------- | ----------------- |
| Orders    | Order Service     |
| Stock     | Inventory Service |
| Payments  | Payment Service   |
| Shipments | Shipping Service  |

Other services may read events.

They do not update others' data.

---

# Step 8 — Database per Service

Never one shared database.

Bad:

```text
One ecommerce_db
```

Good:

```text
order_db
inventory_db
payment_db
shipping_db
```

Later each can scale independently.

# Step 12 — Ubiquitous Language

Very important in DDD.

Everyone uses same words:

Use:

* Reserve Inventory
* Authorize Payment
* Create Shipment
* Complete Order

Avoid teams saying:

* "lock stock"
* "hold stock"
* "freeze stock"

One term only:

Reserve Inventory.

That avoids integration bugs.
